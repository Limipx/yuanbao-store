## 零、一句话总览

**引擎是标准 Lua 5.1（非 LuaJIT），标准库被裁剪 + 被引擎扩展。**

```
_VERSION = Lua 5.1
jit = nil     ffi = nil     ← 不是 LuaJIT，FFI 优化路线全部作废
bit = table（12 成员，含 ror）
os  = 只有 date / time / timeMs
```

---

## 一、不是 LuaJIT（推翻此前推测）

```
jit = nil
ffi = nil
```

**此前我根据截图里 `fill/copy/gc/load/string/arch/os` 七个字段，
推测"引擎是 LuaJIT 且 FFI 可见"——这条错了。**

那七个字段确实与 LuaJIT `ffi` 库成员同名，但实机 `ffi` 是 nil。
（截图的来源另有一说，或为引擎内部 C 层符号表，未确证。）

### 后果（重要）

| 原计划 | 状态 |
|---|---|
| `ffi.new("int64_t")` 原生 64 位整数做 RSA/大数 | ❌ 作废 |
| `ffi.new("double[512]")` 指针遍历加速 matvec | ❌ 作废 |
| `tonumber(cdata)` 处理 64 位整数 | ❌ 作废 |

**位运算只能靠引擎 `bit` 库；大数只能靠 BN（double 模拟）。**

## 二、math 库：34 个成员，被引擎扩展过

```
abs acos approximately asin atan2 atan ceil clamp cos cosh deg exp
floor fmod frexp huge ldexp lerp log10 log max min mod modf pi pow
rad random randomseed sin sinh sqrt tan tanh
```

### ⚠️ 修正一条旧结论

旧文档《Lua5.1数学库缺失与实测坑》写：
> `math.tanh` ❌ 不存在（需脚本内自带实现）

**实机：`tanh: function`（存在）。**
同理 `math.pow` 实机**也存在**（旧文档对 5.1 的判断是对的，但"5.5 移除"那条导致我在脚本里一律禁用，属过度保守）。

旧结论的来源是把"标准 Lua 5.1 + Lua 5.5 沙盒"的表现当成了引擎表现。
**引擎的 math 是扩展过的，还多了 Unity 风格函数**：
`clamp` / `lerp` / `approximately` / `mod`（这些标准 Lua 5.1 没有）。

### 实践建议

- 新脚本：**可以直接用 `math.tanh` / `math.pow`**，比自带分段实现更快
- 已有脚本里的自带 `_tanh` / `^` 运算符**无需改动**，属于无害冗余
- 但**不要依赖 `math.mod`**（标准 5.1 无，引擎有）——跨环境移植会断

## 三、string 库：15 个成员，含引擎扩展

```
Trim byte char find format gmatch gsub len lower match rep
reverse split sub upper
```

**`string.split` 存在，`string.Trim` 存在。**

### 但有一个已知坑（我踩过）

自写的 `Split` 若用 `gmatch("[^,]+")`，**空字段会被跳过**：
`"a,,b"` 得 2 个而非 3 个。

引擎的 `string.split` 分隔符行为**未实测**，使用前先验：

```lua
-- 建议：先探一次
local t = string.split("a,,b", ",")
print(#t)   -- 看是 2 还是 3
```

`string.buffer = nil`（Lua 5.4 特性，不存在）。

---

## 四、table 库：只有 8 个成员，**没有 unpack**

```
clone concat equal getn insert remove sort
```

- ❌ **无 `table.unpack` / `table.pack`** → 必须用全局 `unpack(...)`
- ✅ 引擎扩展了 `table.clone`、`table.equal`（标准 5.1 没有）

`table.equal` 对"比对两份账本/状态哈希"很有用，省得自己写深比较。

---

## 五、os 库：只有 3 个

```
date  time  timeMs
```

**`os.clock` 不存在——用了必崩**（这是老坑，实机再确认）。

`os.timeMs` 是全部时间调度的唯一基准。
**铁律不变**：按时间推进的调度一律用**绝对时间戳**，
绝不每帧累加固定步长（TTS v3.1 只播 1 个音节就栽在这）。

---

## 六、bit 库：12 个成员，含 ror

```
arshift band bnot bor bswap bxor lshift rol ror rshift tobit tohex
```

- ✅ **有 `ror`**（我上一轮凭记忆说"只有 rol 没有 ror"是错的，已修正）
- **是有符号 32 位**：`lshift(1,31) = -2147483648`（不是 2147483648）
- `tohex(0xFFFFFFFF) = "ffffffff"`
- `bit32 = nil`（Lua 5.2 的，不存在）

### 有符号 32 位意味着什么

所有位运算结果都要当作**有符号**处理。取高位的正确姿势：

```lua
-- 取 32 位无符号值
local function u32(x)
    if x < 0 then return x + 4294967296 end
    return x
end
```

## 七、大数：double，2^53 之后不可区分

```
2^53     = 9.007199254741e+15
2^53 + 1 = 9.007199254741e+15   ← 完全相同
```

**BN（大数库）是必须的，不能靠 double 硬算。**
RSA / SHA-256 / 大素数判定全部依赖自实现的 BN（按 32 位 limb 存 double）。

---

## 八、io 库：0 个成员

**无任何文件读写能力。** 所有数据只能：
- 走 KV 表（`Data.Map` 系列）
- 或 `print` 到日志窗口人工复制

这直接决定了"导出数据"的唯一姿势：**分块 print**（TTS v3.3 的 `Dump` 就是这么做的）。

---

## 九、coroutine：7 个成员全在

```
create isyieldable resume running status wrap yield
```

**协程可用。** 异步/泵逻辑除了"广播自驱动 + 计时器"之外，
多一条 `coroutine` 路线可选（用于多步计算分片，避免单帧阻塞）。

---

## 十、debug：只有 1 个

```
traceback
```

无 `getinfo` / `gethook` / `getlocal`。
调试只能靠 `print` + `debug.traceback`，拿不到调用栈细节。

---

## 十一、loadstring：存在（与旧记忆冲突，需再确认）

```
loadstring = function
```

旧记忆写的是：**`loadstring` 实测返回 nil，不可用。**

两者不矛盾的可能解释：
- `loadstring` 是 function（能被引用）
- 但**调用后返回 nil**（引擎可能禁用了编译后端，或 obfuscator 环境限制）

**待真机确认的唯一姿势**：

```lua
local f = loadstring("return 1+1")
print(type(f))              -- function 还是 nil？
if f then print(f()) end    -- 能执行吗？
```

在确认前，**字符串→可执行逻辑一律走自写编译器 + VM（LuaVM 桥接）**，不要赌 loadstring。
