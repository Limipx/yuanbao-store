# KV 文件系统与去中心化文件夹

> 更新：2026-10-15（第三轮：全服共享 + 收敛性实测 + 版本向量陷阱）
> 状态标注：【已测】= 沙盒多房间仿真确认　【未测】= 真机未验证
> **⚠️ CloudSever 已作废，云服现行走 `Data.Map` 系列（13 函数）**

## 一、核心洞察：一个广播凭什么能全服共享

**云服全服广播本身就是原子广播** —— 一次发送，所有房间都收到。
分布式系统的经典结论：**原子广播和共识是等价的**，有了它共识变平凡。

所以**不需要 Leader、不需要投票、不需要 PoW/PoS**。全部"共识"就是一句排序：

```
按 (Lamport时钟, 房间ID, 序号) 排序 → 重放 → 所有房间必然得到同一棵树
```

- Lamport 时钟保证有因果关系的排对
- 无因果关系的靠房间 ID **确定性打破并列**
- **没有人投票，但所有人都同意谁是最后写的**

## 二、与区块链的同构关系

| 区块链 | 本系统 |
|---|---|
| 节点 | 云服房间 |
| gossip 网络 | 全服广播 |
| 账本 | 房间数组里的追加日志 |
| 哈希链 | 每房间一条链（`prev` 指向本房间上一条） |
| Merkle 树 | 全局状态根，用来比对"我们是否一致" |
| 全节点复制 | 每个房间存全量 → 抗房间关闭 |
| 出块 | 多条操作打包进一条广播，摊薄延迟 |

### 但三件事不需要

- **PoW/PoS** —— 那是给陌生人建立信任用的，这是许可链
- **Leader 选举** —— 全序通道已经送上门了
- **代币激励**

> 诚实说：这东西更接近 **CRDT + Merkle-DAG（git/IPFS）**，不是比特币。

## 三、⚠️ 最致命的坑：版本向量必须用连续水位

**这是唯一会让系统彻底无法收敛的缺陷。**

### 错误做法

版本向量用「最大 seq」。乱序投递后：

```
B 拿到 1–24 和 100–112
VV 记成 112
A 以为 25–99 都有了 → 永远不再补发
```

**实测：卡在 12 条一动不动。**

### 正确做法

改成**连续水位**（TCP 累积确认那个语义）：

```
VV[room] = 已从该房间收到的最大"连续"序号
```

这样 25–99 的空洞才会被识别并请求补发。

## 四、第二个坑：同步时互相冗余

所有房间收到心跳后都回**同一批最低的 12 条**，互相完全冗余，
**收敛速度不随房间数提升**。

**修正**：改成排序前缀 + **按自身 rid 散列抓放大块**。

## 五、混沌测试实测

```
8 房间 / 226 次随机操作 / 随机关闭 12 次 / 随机重复投递
→ 最后 10 个存活房间全部持有完整 226 条
→ 单一 Merkle 根，坏条目 0
```

**房间关了数据不丢，靠的是全量复制。**

## 八、保证到哪（说清楚边界）

### ✅ 做到的

- 最终一致性
- 抗房间关闭
- 抗重复投递
- 抗伪造（哈希不匹配直接丢）
- 房间重启数据完好

### ❌ 做不到的

- **强一致** —— 读本地，落后最多一个同步周期，CAP 下只能选 AP
- **所有房间同时关闭 → 数据全丢** —— 不用 KV 表就没有跨房间生命周期的存储，**这是硬边界不是 bug**

### 🔧 没做的

- 崩溃重放（WAL）
- `Compact()` 只逻辑剪枝，**不回收空间**
- 权限加密

## 九、部署要点

1. **`msgId` 必填** —— 必须是触发器里预设那条广播的 ID（形如 `m177358728257565`），
   **自己编一个没人收**
2. **日志量大时把 `blockMax` 调到 30–50** —— 200 条日志从零同步约 17 轮 × 20 秒 ≈ 6 分钟，
   调大能压到 1–2 分钟
3. 导入后先 `NetProbe()` 看广播通不通，再 `Digest()` 对比几个房间的 `root` 是否一致

## 十、限流（务必记住）

| 类型 | 每分钟上限 |
|---|---|
| 设置类 | `30 + numPlayers × 10` |
| 获取类 | `30 + numPlayers × 10` |
| **排行榜** | **`5 + numPlayers × 2`（最严格）** |

排行榜配额约为 KV 的 **1/5**，**绝不能进高频逻辑**。
