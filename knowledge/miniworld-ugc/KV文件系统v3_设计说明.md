# KV 文件系统 v3 —— 框架全改设计说明（CRDT op-log 架构）

> 配套：`KV文件系统_云服版v3.lua` / `.txt`（md5 `259634e0`）
> 理论依据：`KV环境一致性_前沿文献研究.md`
> 实测：`_v3_test.py`，lupa 真跑，**19/19 通过**

---

## 一、先回答：多房间并发下能不能保证数据

**分场景，不能笼统说"能"：**

| 场景 | v2 | **v3** |
|---|---|---|
| 单房间、单写入者 | 勉强可用 | ✅ |
| 多房间并发**读** | ❌ 永久陈旧缓存 | ⚠️ 可能陈旧，但**能检测**（`Status` 会提示） |
| 多房间并发**创建** | ❌ 互相覆盖 | ✅ **20/20 全保留** |
| 多房间并发**移动同一对象** | ❌ 丢失更新 | ✅ 冲突显式检出，裁决一致 |
| **move 成环** | ❌ 树直接损坏 | ✅ 检出并拒绝 |
| 跨房间（延迟 3 tick） | ❌ 数据丢失 | ✅ 多轮同步后收敛 |
| 进程被杀后重启 | ❌ ID 复用 | ✅ seq 从日志恢复 |

**做不到（这是环境决定的，不是实现问题）：**

1. **线性一致** —— 无法保证读到"全局最新"。无租约、无法定人数、无同步时钟。
2. **跨键原子提交** —— 服务端无事务。两次 `set` 之间没有原子性。
3. **进程被杀时未发布的本地 op 会丢** —— 等于没提交，语义上可接受。
4. **瞬时全局一致** —— 只能保证"持续通信后最终收敛"。

## 二、v2 的五个致命问题 → v3 的解法

| # | v2 问题 | v3 解法 | 依据 |
|---|---|---|---|
| 1 | 缓存永不失效 | 每次 Sync 强制**全量重放**，不返回未验证缓存 | — |
| 2 | 读-改-写无版本校验 | **只追加 op-log**，永不覆盖已有值 | OpSets / CmRDT |
| 3 | ID = 时间戳+随机数（并发撞） | `ID = siteId.seq`，siteId 由 **uin 派生**，零分配零碰撞 | 文献 §9 |
| 4 | 多键操作非原子 | 一次 move **只生成 1 条 op**，1 次批量发布 | 文献 §11 |
| 5 | 限流失败静默入队 | 失败**显式返回 ERR**，绝不假成功 | — |

## 三、Key 布局（全部 ASCII、无空格、≤50 字节）

```
R.<app>               根（仅提示性，可被覆盖，丢了能自愈）
P.<app>.<site>        ★ 站点指针（权威，只该站点自己写，永不冲突）
                      值: <分片数>|<最大seq>
L.<app>.<site>.<n>    第 n 个不可变 delta 分片
                      首行: H|<site>|<minSeq>|<maxSeq>|<count>
```

### 为什么必须有 `P.<site>` 这个键（本轮实测挖出的坑）

第一版只有根键，Sync 完全依赖根里的 `shards` 表。**实测场景 4 直接失败（12 个对象只拿到 3 个）**：

两个站点同时 read-modify-write 根 → 后写覆盖先写 → 先写者的分片信息从根里消失 → 其他客户端永远找不到它的分片 → **永久数据丢失**。

修法是**去中心化**：权威信息（我有几个分片）放进只有我自己写的 `P.<site>`，根键降级为"提示性站点列表"，丢了也能自愈。

## 四、op 格式

```
dot|type|obj|arg1|arg2|hlc|dep
```

- `dot` = `<siteId>.<seq>` —— 全局唯一、本地确定、**重启后从日志恢复**
- `type` = `mk` / `mv` / `rm` / `wr`
- `hlc` = `<pt>:<ct>` —— 只用于**确定性全序**与新鲜度展示，不承担因果
- `dep` = 依赖的 dot 列表 —— **因果由它承载，不由 HLC 承载**

全序键：`%013d:%05d:%s`（pt, ct, dot），保证字典序 == 数值序，所有客户端排序结果一致。

## 五、并发裁决规则（确定性，所有客户端一致）

1. **并发 move 同一对象**：两条 mv 的 dep 互不包含 → 记 `concurrent_move` 冲突，**全序靠后者胜**，不产生双父。
2. **move 成环**：应用前检查新父的祖先链是否含自己 → 记 `cycle`，**拒绝应用**。
3. **并发 删除/修改**：记 `concurrent_rm` 冲突，全序裁定。
4. **重放是纯函数**：op 集合相同 → 状态必然相同。这是收敛的根本保证。

## 六、配额实测

5 客户端完成全部创建+并发移动：

```
累计 get=399  set=27
平均每客户端 set 5.4 次
```

配额是 `(30 + 在线×10)` 次/分钟，5 人在线 = **80 次/分钟**。实测 **5.4 次**，有 15 倍余量。

代价模型（每批 m 条 op）：

| 操作 | get | set |
|---|---:|---:|
| 批量发布 m 条 op | 1 | 2（分片 + 指针）|
| 双向同步（无差异） | 1 + 站点数 | 0 |
| 双向同步（有差异） | 1 + 站点数 + 缺失片数 | 0 |

**关键：发布 m 条 op 的代价与 m 无关** —— 这就是批量 delta 的价值。

## 八、已知限制（诚实版）

1. **没有 GC** —— op-log 只增不减，长期运行会增长到 2MB 上限。需要**快照压缩**：某客户端重放后写快照，把旧分片加 GC 候选（文献 §10 的因果稳定判定）。这是文献里的第五阶段，本版未实现。
2. **站点发现机制弱** —— 跨房间要靠 `peerSites` 属性预置，或靠根（会被覆盖）。同房间应走**广播**交换站点 ID（本版未接广播）。
3. **并发删除+修改的冲突判定偏松** —— `wr` 不参与 `_headOf`，所以"删除 vs 改内容"目前不报冲突。需要更严的语义时再收紧。
4. **未发布的本地 op 会随进程死亡丢失** —— 语义上等于没提交。
5. **`Data.Map` 的返回码我假定 `code==0` 为成功** —— 若引擎不同，改 `_ok()` 一处。

## 九、与前沿文献的对应

| 文献/系统 | 本版落地位置 |
|---|---|
| OpSets（Kleppmann, arXiv 1805.04263） | 目录树 = 对象稳定 ID + move op 推导父关系 |
| CmRDT / op-based CRDT（Shapiro 等） | 只追加 op-log，幂等合并 |
| Hybrid Logical Clock（Kulkarni 2014） | `(pt, ct)`，仅全序与新鲜度 |
| Yjs delta 同步 | 按 `_knownTop` 只拉缺失分片，不全量回传 |
| Merkle 根比较 | 根带 hash，无差异零写 |
| RAMP（Bailis, SIGMOD 2014） | **未采用** —— 原样部署需多轮 prepare/commit，配额不允许；改用"一次 move = 一条 op"达到同等效果 |
| Anna 的 lattice（SIGMOD 2018） | 思想下沉：每个 value 定义 merge 语义，不依赖服务端 |
