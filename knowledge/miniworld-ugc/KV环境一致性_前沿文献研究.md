# KV 环境一致性前沿文献与技术方案调研

## 摘要

这个环境不可能靠一次 `get`/`set` 获得线性一致或跨键原子提交：服务端既无 CAS、事务、多键原子写入，也无法执行协调逻辑；客户端之间只有不可靠的房间广播和一次只能取回或覆盖一个 value 的 KV。可行目标是**强最终一致 + 因果可检测 + 收敛**，实现方式不是把服务端变成数据库，而是把每个可变对象表示为只追加的操作日志，以幂等、可交换、可合并的 delta-state CRDT 承载；Yjs 的官方实现已将变更编码为交换、结合、幂等的二进制 update，并支持按目标状态向量只编码缺失差异，正适合“读写共享、每分钟只有几十次”的约束[6]。目录树应使用每个节点一条“父指针日志”，而不是原地 LWW：并发 move 以确定性全序裁定，并显式检测父环；LWW-Register 只能作为应用可接受的冲突策略，不能保证“不丢数据”。HLC 可用作稳定、人类可读的全序与新鲜度线索，但物理时钟偏差、房间隔离和任意客户端回拨会破坏其因果保证，因此必须同时维护紧凑版本上下文。RAMP、完整 vector clock 和逐键 tombstone 均不适合极低配额；推荐以“本地 op-log + 批量 delta + 最小因果向量 + 机会性广播 + 周期反熵”为主，并将每批写压缩到接近 1 次 set。雪花 ID、随机 UUID、本地时钟都不可靠；ID 应优先由“客户端固定短名 + 单调序号 + HMAC”构成，或用内容哈希寻址不可变 op 后再用稳定名引用。

## 一、硬约束决定了“复制数据类型”而不是“乐观锁”才是正确抽象

**裸 KV 没有协调能力，所以客户端必须携带足够的合并语义。** 本服务的接口只有 `get(key)`、`set(key, value)` 和 `del(key)`，服务端不能执行 CAS、版本校验、事务、计数器、锁或可靠通知。客户端可随时离开，进程可随时被杀。若继续使用“读取当前值—本地修改—覆盖写回”，两个客户端读到同一版本后再写，先到者必然被后写覆盖；这不是重试次数不足，而是接口没有提供被覆盖前的版本比较。Shapiro 等人提出的 CmRDT/CvRDT 理论正是把这类冲突从互斥转移到数据类型：让更新本身在副本间交换、结合、幂等地合并[1]。Liang 与 Feng 对 op-based CRDT 的研究也把正确性定义为：当两个节点看到同一组操作时，它们可计算到相同的抽象状态[1]。

`key≤50` 字节、可打印、排除空格，意味着不能把长 vector clock、UUID、随机后缀或路径原样塞进 key；`value≤2MB` 则允许每个对象承载一个小型 op-log、delta 或快照，但不允许无限增长的元数据。`(30+在线人数×10)` 次/分钟的共享令牌桶是更严格的约束：若 5 人在线，桶约 80 次/分钟，若 50 人在线则约 530 次/分钟；所有同步还必须与正常读共享预算。因此“每次本地写都立刻上传”“每次合并都全量回传”“为每一条 tombstone 单独写键”都不成立。

**线性一致和跨键 ACID 不可达。** 单次 `get` 只能看到某个副本某一时刻的值，没有法定人数、租约、时钟同步验证或原子提交协议，就不能保证读到“全系统最新”值，也不能阻止两个客户端同时以旧值开始计算。无协调读本质上只能达到最终一致；进程被杀更会让所谓“当前事务”失去全局协调者。能实现的是：每个已提交 op 最终被所有存活且能通信的客户端收到；冲突由数据类型决定而非随机覆盖；读上下文可检测出“是否可能陈旧”；客户端共同看到的前缀与因果序最终一致。

| 模型 | 本环境是否可达 | 判定依据 |
|---|---:|---|
| 最终一致 | 是 | 可靠 KV 和持续反熵可交付全部幂等 op |
| 因果一致/因果检测 | 有条件可达 | 客户端维护紧凑因果上下文；进程重启可恢复 |
| 强最终一致（SEC） | 是 | op 全序、幂等合并、全交付 |
| 读己之写、单调读 | 有条件可达 | 会话缓存并携带因果上下文，但不跨进程自动成立 |
| 读后写、单调写 | 有条件可达 | 本地按因果依赖发布；仅对已知依赖成立 |
| 可串行化/快照隔离 | 否 | 无全局版本、谓词读、原子提交和并发控制 |
| 线性一致/外部实时序 | 否 | 无同步物理时钟认证、租约或一致核心 |
| 跨键原子提交 | 否 | 两次 `set` 之间没有服务端原子性 |
| 自动死锁/冲突避免 | 否 | 无锁服务，客户端只能力导合并或应用级处理 |

## 二、CRDT 选型应优先选“可批量编码”的类型，而不是传统 counter 集合

**state-based 适合中心化合并，op-based 更适合本场景的只追加日志。** 经典 CRDT 分类是 state-based（CvRDT）和 operation-based（CmRDT）。前者把本地状态编码后发送给其他副本，由单调连接运算 `merge` 形成半格；后者发送生成的操作，并要求可靠的因果交付或接收端幂等重放。纯 op-based 不应把“读取当前值”作为应用操作的一部分，而应从初始状态开始重放幂等 op[3]。本环境没有可靠广播，也没有服务端对 op 排序，但客户端可以把 op 持久化为 KV 中的不可变 value，再由其他客户端拉取；所以落地形式是“**以 state 为载体承载 op-set 的 delta**”，不是把整个应用状态反复回传。

G-Counter 和 PN-Counter 适合在线人数、得分等可单调或可抵消的计数器，但每次 `inc` 理论上需携带节点计数，且 PN-Counter 必须同时记录增、减事件。对低频遥测可勉强使用；对“每次点击”的房间计数不应直接写入 KV。G-Set 只增不删，合并是并集；2P-Set 把 add 与 remove 分成两集，删除不可逆，适合权限、永久封禁。OR-Set 为每次 add 附加唯一 tag，remove 必须精确删除当时已知的 add tag，合并不会丢失并发 add，是多人集合的首选；代价是 tag 和 tombstone 会累积。

LWW-Register 虽然可用 HLC 或内容哈希做时间戳，且在现代 CRDT 框架中容易定义，但它按“最后写入者胜”丢弃其他并发值[3]。如果目标是“不丢数据”，它只能作为可接受的策略，不应成为目录树的唯一真相。Kleppmann 等人在 OpSets 中明确把 map 键和 list 元素建模为多值寄存器，并说明 LWW 只是在并发赋值中任选其一[3]。其优势是实现轻量、冲突可检测；劣势是设备离线后恢复的上传可能覆盖别人更新。

| 类型 | 适用对象 | 本环境代价 | 推荐度 |
|---|---|---:|---:|
| G-Counter | 只增统计 | 每节点单调值，合并廉价 | 中 |
| PN-Counter | 可抵消计数 | 需维护增、减两点 | 低—中 |
| G-Set | 永久成员、已存在集合 | 仅增长；合并为并集 | 高 |
| 2P-Set | 添加后不可恢复删除 | 两集合永久增长 | 中 |
| OR-Set | 并发添加/移除 | tag 与 tombstone 增长 | 高 |
| LWW-Map | 可覆盖字段 | 每次写约 1 set；并发丢失 | 中 |
| RGA/Logoot | 文本/有序列表 | 每元素元数据较大 | 中—低 |
| 父指针 op-log 树 | 目录、对象移动 | 需环检查、GC；适合批量 | 高 |

**序列 CRDT 可以复用，但不应直接成为房间状态的主存储。** RGA 与 Logoot 以“在唯一元素 ID 之后插入”的位置 ID 实现文本序列，能保证字符不丢失，却使每个字符携带 origin、offset 或随机 UID。Yjs 把文档更新压缩成高度压缩的二进制格式，并支持按目标状态向量生成缺失差异；合并 update 能去除重复信息，但合并并不回收已删除内容，要减小文档仍需加载到 Y.Doc[6]。这证明 delta-state 和状态向量能显著节省带宽，也证明 tombstone 仍是独立问题。Automerge 适合长期协作文档，但其 change/op 历史元数据通常比 Yjs 更重；在本场景若只需“稳定树 + 少量字段”，不应照搬完整 JSON CRDT。

## 三、目录树必须用因果可判定的 move 日志，而不能依赖最后写父指针

**推荐的目录模型是“对象身份稳定、父关系由 op 推导”。** 每个逻辑对象拥有一个 ≤50 字节的可打印稳定 ID，例如 `o:<roomId>:<appPrefix>:<shortId>`，其内部 value 存放内容哈希、应用字段快照、创建者证明和因果向量。目录关系则使用专门键，例如 `tree:<roomId>:<objId>`，value 是只追加的父 move op 日志。每条 op 形如：

```
(opId = siteId#seq, parent: prevObjId|null,
 target: objId, causalDeps: compactContext,
 hlc: (pt, count), meta: optionalAppData)
```

这里的 `parent` 是 move 发生前的旧父对象，不是只写新父。读取者从初始“无父”出发重放所有已交付 op，得到每个对象的最新父；查询路径则在线计算。这样“移动 A 到 X”和“移动 A 到 Y”都保留在日志中，不会像单值 LWW 那样消失。Kleppmann 等人在 OpSets 框架中给出了原子树 move 的形式化规格，并证明一种已有算法满足所需性质，而另一些已发表算法不满足[3]；这表明 move 不是简单加锁就能解决，必须规定全序与确定性解释。

**并发 move 既可能冲突也可能产生环，必须在合并时显式处理。** 如果两个客户端并发执行 `move A under X` 与 `move A under Y`，合理语义不是“必然保留两个父”，而是让所有副本按同一全序裁定一个结果，例如比较 `(hlc, siteId, seq)` 后后序胜，同时把被覆盖的 move 标为冲突。移动造成环有两种路径：一是直接把对象移入自身后代；二是跨客户端并发形成 `X→Y→X`。前者可在应用单条 op 时拒绝；后者无法只看局部最新父关系发现，因为两条因果无关 op 可能先被不同客户端接收。因此必须对所有对象维护“已重放该 op 后的传递祖先集合”并检测环。发现环时不能任意 drop op，而应回退到稳定的确定性策略，例如“保留字典序较大的合法边，另一 move 转为冲突边”，并在 UI 显示“目录冲突”。

**LWW-Register 只适合无父子结构、允许覆盖的字段。** 文件内容哈希、昵称、数值设置可写成 LWW，但目录父关系和权限继承不能。一次 `set(parentKey, newParent)` 完全无法表达“我从版本 V 发起移动”，而服务器又不返回旧值，冲突双方都会成功。即使加入 HLC，也不能区分并发和“后发生的快但迟到”；即使维护历史，也无法靠两次独立写同时更新旧父与新父。因此文件移动的推荐代价不是 2 次并发 `set`，而是 1 条不可变 move op，由反熵或机会广播交付。

## 四、因果上下文应小而可推进，版本向量只用于判断而非阻塞

**版本向量表达的是“我看到什么”，不是“全世界的真值”。** 经典版本向量为每个副本保存一个序列号；若 `V(a)≥V'(a)` 且 `V(b)≤V'(b)` 对所有副本成立，则前者因果后续于后者；否则可能并发。它天然随参与者数量增长，且需要客户端在生成 op 前收到依赖 op。Dotted Version Vector（DVV）用一个 `dot` 表示某个站点的最近事件，再用紧凑因果上下文表示其后发生的 dot 集合，从而降低纯 per-replica 向量的部分开销；但若参与者数量本身很多，仍然无法压缩到几十字节。

本场景应维护两种上下文。第一是**本地单调序号**：每个客户端有固定短 ID，序号在本地严格递增；op ID 因此本地确定、全局唯一。第二是**可截断的因果摘要**：只记录“本客户端直接依赖的其他活跃站点最近序号”。同步握手先比较双方摘要，只请求缺失 dot；收到 dot 后才允许以其为依赖生成新 op。进程被杀后本地序号必须持久化，不能从 0 重启，否则新 op 会复用旧 ID，导致幂等合并失效。

**“读到陈旧值”只能以因果风险表示，不能保证新鲜。** 读路径应返回 `(value, compactContext, hlc)`，客户端把读上下文缓存为会话下限。若后续一次读返回的 context 不后续于本地下限，就提示“可能有陈旧读”；若依赖的 op 尚未送达，就把字段标为 `unknown`。这是一种显式新鲜度检测，而不是返回 false 的 CAS。Yjs 的 `encodeStateAsUpdate(doc, targetStateVector)` 正是按目标状态向量只编码缺失差异，而不是全量发送，可以直接借鉴其同步思想[6]。

HLC 由 Kulkarni 等人提出，组合物理时间和逻辑计数，并保持在 NTP 附近；该工作给出了 64 位布局，以 48 位近似物理时间、16 位逻辑计数[2]。它优于 Lamport 时钟之处在于保留近似墙钟，便于日志排序和过期清理；优于 vector clock 之处在于长度不随站点线性增长。但它不能替代因果向量：NTP 偏差、虚拟机暂停、房间隔离、未交流站点都会让 `hlc(a)<hlc(b)` 不能推出因果。HLC 在报告里只负责稳定全序、冲突展示和 GC 截止时间；关键因果依赖仍由站点序号承载。

## 五、RAMP 的理论有用，但原样部署不适合极低写配额

**RAMP 解决的是“多分区读原子可见”，不是本场景的裸 KV 原子提交。** RAMP 由 Bailis、Fekete、Ghodsi、Hellerstein 与 Stoica 提出，正式论文题为 *Scalable Atomic Visibility with RAMP Transactions*，发表于 2016 年 ACM TODS（会议版为 SIGMOD 2014）[4]。其目标称为 Read Atomic（RA）：其他事务要么看到某事务的全部更新，要么一个也看不到。RAMP 通过为参与键保存版本元数据、分区独立执行以及无协调提交，实现即使部分失败也保证提交并减少服务器间通信；论文报告在 100 台服务器上线性扩展[4]。

核心思想是 write 阶段把更新与事务/版本元数据一起写入各分区；read 阶段若发现某个键属于尚未完全可见的事务，则根据变体获取其余相关版本或等待，从而保证不出现“断裂读”。Fast RAMP 的写通常包含准备版本与提交；Hard RAMP 需要更多依赖元数据；Soft RAMP 通过客户端重建依赖。其代价不能一概而论：读可能需要额外往返，写会复制事务版本元数据，版本历史也会放大存储。本次可访问的论文页没有展开完整 prepare/commit 字段与逐算法往返，因此不能编造固定数字；但能从架构判断，RAMP 假设服务器可为每个分区保存并检索元数据，而不是把元数据装进单一 2MB value。

**文件移动“改两个父目录”正好暴露了 RAMP 与本环境的不匹配。** 若把旧父、新父、对象头各存一个 KV，真正的原子性要求三条写要么同时生效。RAMP 通过多版本和读路径修复断裂读，不提供客户端崩溃后自动完成提交；若协调客户端在准备阶段之后被杀，其他客户端必须识别孤儿 prepare、寻找事务状态并清理。这里没有专门事务键、可靠锁或租约，完成协议只能在另一个客户端用额外 get/set 模拟，写入次数和复杂度都违背配额目标。即使强行走 RAMP，也不能把“所有键全可见”升级为外部线性一致。

落地建议是借鉴 RAMP 的“不可变 prepare 记录 + commit 指针”，但把跨键对象放进同一条 op-log：本地先生成 `move` op，把三个对象的新状态作为同一 op 的确定性投影，一次批量 `set` 上传 delta。读者只在没有看到对应依赖时把目录视图标记为不完整。若真的跨两个不可合并对象，则把两个对象设计为同一 log 的子键，而不是独立全服键。

## 六、Anna 的 lattice 思想可下沉，服务端仍无法提供原子性

**Anna 的关键价值是“用 lattice 组合可交换更新”，而不是把它当黑盒 KV。** Anna 由 Wu、Faleiro、Lin 与 Hellerstein 发表于 SIGMOD 2018，论文题为 *Anna: A KVS for Any Scale*。其设计把多种一致性模型实现为格组合，利用无协调执行实现水平扩展；该结果依赖服务端对 lattice merge、版本和复制的支持。本场景无法部署服务端 lattice，但客户端可以照搬同一数学结构：把每个 value 解释为某种半格状态，例如 OR-Set、G-Counter 或单调递增父边集合，`merge` 由客户端在本地计算后写回。

Anna 的“any-scale”和“coordination-free”不应被理解为“客户端不需要处理冲突”。若两个客户端各自生成不同的不可交换覆盖值，服务端仅按最后一个字节保存，结果仍是后写覆盖；格只有在类型语义、幂等标签和依赖上下文齐全时才成立。所以 Anna 的适用性限定为**数据结构层思想下沉**：用 lattice/CRDT 给每个对象定义 merge，不假设 KV 自身提供一致性。

**Feral concurrency control 与 Bolt-on 同样只能做设计参照。** Lloyd 等人的 COPS（SOSP 2011）通过显式因果依赖、依赖检查与反熵实现无锁、高可用存储的因果一致；Bailis 等人的 Bolt-on Causal Consistency（SIGMOD 2013）则把因果依赖跟踪加在已有弱存储上。二者都依赖稳定的依赖元数据、服务端因果感知读或后台同步基础设施。本场景可复制“读时携带依赖摘要、反熵补齐缺失版本”，但不能复制“服务端在读取分区时阻止或修复断裂依赖”。Facebook 的 Feral Concurrency Control 的核心是利用应用语义减少协调，这个原则适合用于识别“哪些业务状态可交换”；没有取得可引用的原始论文全文时，不对其算法步骤作精确引用。

## 七、Merkle-DAG 非常适合发现差异，但每次写全链哈希仍太贵

**内容寻址的价值是增量定位和完整性，而不是每次同步发全部历史。** IPFS 把数据组织为 Merkle DAG，每个内容地址可由其数据确定；改变任意块都会沿父链接改变根哈希，因此比较根即可判断两棵树是否可能一致，再沿子哈希递归定位变化块。对本环境可直接类比：把一批 op-log 的哈希数组作为目录头，将每个 2KB～几百 KB 的 delta 写成独立 KV 对象，其 key 为受限制的可打印短名或内容地址别名。同步时先比较根哈希和分层哈希，只请求差异 delta；新客户端仍需拉取完整可达历史以计算当前树。

**Merkle-DAG 必须与 op-log 结合，不能让哈希成为对象身份。** 若目录项键直接是内容哈希，每次更新会生成新 key，而 key 长度、可打印字符与路径稳定性都受限；同时父目录也会因子对象变化而更新，造成级联写。推荐结构是稳定对象 ID 作为用户可理解名称，value 中包含内容哈希；另设 `cas:<room>:<shortHash>` 保存不可变 delta。这样比较哈希可快速找差，但移动、删除和重命名仍由 CRDT 语义解决。

写代价模型如下：一次安静期后的本地批包含 `m` 个 op，客户端先确认自己的日志头为 `h`；理想情况下只需 1 次 `set` 上传 `[h+1…h+m]`，若需回指稳定根则再追加 1 次。房间内广播不可靠，不能计入成功交付率；全房间反熵以固定节拍扫描，每次约 1 次 `get(root)`、1 次 `set(delta)`，且只在有差异时写。

## 八、local-first 的关键不是“同步库”，而是 delta、状态向量和 GC 边界

**Yjs 的编码与同步原语最接近本环境，Automerge 更适合富文档而非受限游戏房间。** Yjs 将文档变更编码为交换、结合、幂等的二进制 update，并明确支持按目标状态向量计算差异[6]。`Y.mergeUpdates` 能去除重复信息并压缩，但合并 update 不会垃圾回收删除内容；只有把 update 加载回 Y.Doc 才能减小文档。这意味着“带宽优化”和“内存/历史优化”是两件事。对本场景应定期由某客户端制作一个只包含当前可见元素的快照，并将被稳定覆盖的旧 delta 加入 GC 候选；不应让所有客户端持续持有完整删除历史。

Automerge 的优势是 JSON-like 数据模型和丰富的协作语义，代价是每个 change 携带更细粒度的 op 元数据。Loro、Diamond Types、Hyper Hyper Space 等项目进一步探索可移动树、文本 CRDT 与 Merkle 化 op CRDT，但公开资料未提供其在本场景极端配额下的完整基准。工程上应优先采用 Yjs 的 update/diff 思路，而不是整库引入其对象模型。OrbitDB 适合 IPFS 式内容寻址与 DAG 复制，但其依赖完整 IPFS 寻址、blockstore 和 DHT 语义；本环境没有这些基础设施，只适合借用“内容寻址 delta + 根哈希比对”。

**压缩必须按消息和状态分层。** 短 key 和可打印限制使 Base64 或 Base32 的 256 位哈希明显浪费；若安全模型允许，可使用 SHA-256 截断到 96～128 位、SHA-3 256 或 BLAKE3 128 位前缀，并在服务端可配置升级。op-log 内部应对 `siteId` 做字典编码、对 HLC 做 delta-of-delta、对连续序号做 varint、对相同字段做 schema 编码。房间内广播若可用，传输原始二进制 delta；KV 中才按服务端要求 Base32/Base64 编码。必须保留足够的认证前缀长度，不能只因 key 短就截断到 32 位。

**元数据膨胀是最终一致系统最主要的长期成本。** 每个删除、每个 op tag、每个 tombstone、每个历史父边都会留在 CRDT 中。Yjs 明确说明合并不会回收删除内容[6]，OR-Set 与序列 CRDT 也因需让迟到 op 定位元素而保留墓碑。减少元数据只能从语义入手：把高变化内容拆分为“稳定对象 ID + 大内容 op-log”；用快照替换长期稳定字段；把短生命周期临时对象放到 TTL 或独立房间命名空间；不为调试信息生成不可回收 op。

## 九、ID 必须本地确定、全局唯一且进程重启安全

**时间戳、随机数和雪花 ID 都不可接受。** 时间戳可由 NTP 或本地时钟回拨造成碰撞；弱随机数会并发撞 ID；雪花 ID 要求稳定 worker ID 和单调时钟，游戏沙盒无法保证。时间戳+随机数叠加只是把碰撞概率降低，没有消除。本地缓存随机数源也不是安全证明，反而让重放更难检测。

推荐采用**结构化唯一 ID**：`ID = (siteId, generation, seq)`。`siteId` 由首次进入房间时的可靠 ID 分配机制给出；若没有服务端分配，就使用客户端在初次配置阶段写入的随机 long 作为“站点身份”，而非每个对象随机。`generation` 每次进程重启从持久化存储或协调者递增；`seq` 在 generation 内单调递增。三者共同保证同一进程重启后不会复用旧 op ID。对象 ID 本身尽量短，采用受支持的可打印 Base32 字符，不使用空格。

内容寻址适合不可变 op 和 blob：`h = BLAKE3-128(op bytes)`，以哈希作内部寻址键；但最终用户/游戏对象仍需稳定名，因为内容会变化，两个并发版本内容不同。两者应分层：稳定 ID 解决“这是哪个对象”，内容哈希解决“这个 delta 是否完整、是否重复”。如果服务端允许自定义 value 编码，op-log 可保存 `(opId, dotDeps, hlc, move/parent, payloadHash)`，大 payload 单独寻址；否则把整个小 delta 序列化进同一 value。

ID 生成的最小成本是一次客户端本地计算；首次获取 `siteId/generation` 若需 KV 分配，则约 1 次 get/set，但应跨房间复用且缓存到进程结束。绝对禁止为每个新文件生成一次 UUID 再立即写 KV，否则一次批量创建也会耗尽配额。

## 十、墓碑必须可 GC，但只有因果稳定后删除才安全

**删除在 CRDT 中不是从集合消失，而是加入删除证据。** G-Set 无法删除；2P-Set 把移除者加入 remove set；OR-Set 精确删除 add tag；序列 CRDT 保留 tombstone 以使迟到插入仍可定位位置。Kleppmann 等人的 OpSets 明确指出，list 元素移除后仍在集合 L 中作为 tombstone，直到并发 `InsertAfter` 仍可定位引用，用户视角则只看到拥有值的元素[3]。因此 tombstone 是正确性的成本，不是实现缺陷。

**因果稳定（causal stability）是最实用的删除条件。** 一个 op 对某个副本因果稳定，意味着所有能通过因果路径依赖它的 op 都已交付到该副本；在副本已知依赖已饱和时，墓碑才可安全删除。具体做法是把每个活跃站点的“最大稳定序号”汇总成稳定向量。若某个删除 op 的 `dot ≤ stable(creator)`，且所有已知因果后继均已包含，则该删除标签不再影响未来合并，可以从最小编码状态中删除。实现时必须保守：未收到某客户端任何消息时，不能假设它已稳定；客户端长期离线时其 tombstone 必须保留。

GC 过程不应写多个 key。定期由一个客户端构建“压缩后的当前状态 + 仍然必要的 tombstone + 新根”，对文件做一次 set；其他客户端在反熵时检查根哈希，下载新快照并验证 op 签名/哈希。GC 没有严格周期，可按“日志字节增长超过阈值”或“房间进入安静期”触发；5～10 分钟执行一次反熵、数小时甚至更久才制作快照更符合本配额。必须保留原 op 的可验证范围，若无法验证历史 op，则只能安全删除其 tombstone 之后的冗余元数据，不能重写共识历史。

## 十一、推荐组合把四次操作压缩为一次批量 delta

**推荐的落地架构不是单一 CRDT，而是四层叠加。**

1. **对象身份与内容层**：稳定对象 ID 指向不可变 payload；payload 用 BLAKE3/SHA-256 前缀做完整性。它解决“内容寻址但名称稳定”的问题。
2. **CRDT 状态层**：目录用 move-op 树；集合用 OR-Set；计数器用 G-Counter；可覆盖字段用 LWW，但明确接受其语义损失。它解决“不丢更新”和“并发语义确定”。
3. **因果与排序层**：本地 `(siteId, generation, seq)` 的 dot、紧凑因果摘要负责依赖；HLC 负责稳定展示序与新鲜度；版本向量只同步差异。它解决“陈旧读可检测、并发不混淆”。
4. **传输与恢复层**：Yjs 式二进制 delta、状态向量 diff、Merkle 根比较、机会房间广播和周期反熵共同工作。它解决“低频 KV 下仍能最终交付”。

![推荐组件解决的问题](/data/workspace/dr:KV环境一致性_前沿文献研究/fig_component_mapping.png)
*图 2：推荐组合中每个组件分别解决哪一类一致性或带宽问题。数据来源：本报告基于 CRDT、HLC、RAMP、Yjs 与 Merkle-DAG 文献的工程映射 [2][3][4][6]。*

正常协同路径是：玩家在本地修改，先在不可变 op-log 中追加一条 op；在空闲或数量阈值达到时，把 `[h+1…h+m]` 作为一次 delta 写入对象日志头；房间广播尝试发送该 delta；其他客户端收到后立即并入本地因果状态，未收到者会在下次反熵补齐。文件移动虽然语义上同时改变对象、旧父和新父，却只生成一条 move op，客户端重放后投影成三个视图，因此理想写次数为 1，而不是两次互相竞争的 `set`。

**冲突检测必须显式进入产品体验。** 用户读取字段时同时收到其因果上下文；若本地已知依赖不 ≤ 服务器上下文，提示“数据可能陈旧”。目录并发 move 在合并后检查环和双父，结果进入 `conflicts` 列表，显示“A 被移动至 X，同时另一玩家移动至 Y”，让用户选择保留哪条边。LWW 字段保留全部并发值摘要，至少展示“多个版本”，不静默覆盖。

## 十二、不可达目标与分阶段实施

**不能承诺的目标必须写成产品边界。** 第一，无法保证任意时刻所有玩家看到同一状态；只能保证持续通信后最终收敛。第二，无法保证外部实时顺序或线性一致；HLC 仅提供近似墙钟。第三，无法自动撤销一个已经稳定覆盖的 LWW；只能事后展示冲突。第四，不能保证进程被杀后的正在提交事务自动完成；只能让 op 幂等并支持恢复重放。第五，房间广播不可靠、全服 varId 跨房间共享，意味着“房间级快速收敛”与“全服一致性”必须用不同上下文和 TTL。第六，安全删除需要所有参与者最终确认因果稳定；恶意或不合作的客户端可拖延 GC。

实施应按风险递进。第一阶段把对象改为只追加 op-log，先做 G-Set/OR-Set 和单调计数器，验证 1 次 set 批量发布；第二阶段实现 `(siteId, generation, seq)`、紧凑因果摘要和会话新鲜度；第三阶段实现 move-op 树、环检查与冲突边；第四阶段引入 Merkle 根和状态向量 diff；第五阶段才做保守 GC。每次上线前用 5、20、50 名模拟玩家测量 get/set 预算、delta 大小、落后客户端恢复时间和墓碑增长。若 2MB value 仍无法容纳长期目录，则应把树拆分为“稳定子树 + 定期快照 + 历史 delta”，而不是继续塞元数据。

最终判断是：本环境可以做到不丢数据、冲突可检测和最终收敛，但不能做到跨键原子、线性一致和即时全局新鲜。最经济的工程方案不是 RAMP 式多键 prepare/commit，也不是完整 vector clock，而是把每个对象变成带 dot、HLC 和依赖摘要的只追加 CRDT op-log；用 Yjs 式 delta 编码和 Merkle 根减少传输；以机会广播满足同房间即时性；以低频反熵兜底；再用因果稳定 GC 控制 tombstone。它把昂贵的一致性成本从服务端原子操作转移到客户端确定性合并，正符合“无服务端计算、极低写配额、可恢复客户端”这一极端环境。
