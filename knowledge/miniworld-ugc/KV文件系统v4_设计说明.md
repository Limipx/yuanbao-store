## 一、决定性发现：`UpdateValueAndCallback` 是服务端原子 RMW

v3 的全部并发问题，根源是我**不知道这个接口存在**，一直在用 `Get` + `Set` 两条独立调用。

### 官方原文

> **UpdateValueAndCallback** — "安全更新表中某个 key 下的值，并发存取数据，确保 Key 下的值唯一性"
> "遇到冲突、失败的情况，接口会自动回传最新的数据值，并调用开发者的回调函数，按照开发者自己设定的逻辑进行更新数据，**确保了数据不出错，不会被其他玩家覆盖**"

### 协议（官方示例 + CSDN 官方转载互相印证）

```
引擎拉取当前值  -> 回调(code = KV_UPDATE_GET,   key, 当前值)
引擎索要新值    -> 回调(code = KV_UPDATE_SET,   key, 当前值)  ← 你 return 新值
若期间被别人改过 -> 重新拉取，再次回调（GET -> SET），自动重试
成功            -> 回调(code = ErrorCode.OK,    key, 最终值)
```

等价于数据库里的 `UPDATE ... WHERE version = x` 重试循环，等价于乐观锁 —— **但重试由服务端驱动，不需要客户端轮询**。

### 官方示例（照抄，未改写）

```lua
local function GlobalKVCallback(code, key, value)
    value = json.decode(value) or value
    if code == ErrorCode.KV_UPDATE_SET then
        value = value or {}
        value.updatevalue = 999
        return json.encode(value)      -- ★ 必须 return 新值，且序列化
    elseif code == ErrorCode.KV_UPDATE_GET then
        -- 拿到当前最新值
    elseif code == ErrorCode.OK then
        -- 更新完成
    end
end
Data.Map:UpdateValueAndCallback(GlobalKV, nil, "GlobalKV_Key2", GlobalKVCallback)
```

### 回调识别的三重兜底（引擎枚举值不确定，必须容错）

| 情况 | 处理 |
|---|---|
| `ErrorCode.KV_UPDATE_SET` / `KV_UPDATE_GET` 有独立值 | 直接比对（最理想） |
| 两者与 `OK` **数值相同**（博客说"首次调用 ret 必然为 0"） | 用"值是否等于刚返回的新值"区分 OK 与 SET |
| 枚举表压根不存在 | 首次调用一律按 SET 处理（博客语义） |
| 重试次数 > 6 | **降级为普通 set**（见 §4 为什么这样安全） |

## 二、为什么"合并函数必须是 join"是全部正确性的支点

CAS 重试意味着：**你的合并函数会被调用多次，每次拿到的 base 可能都不一样。**

如果 `mergeFn` 是 `old = old + 1` 这种非幂等操作 —— 重试一次就多算一次。**只有 join（幂等 + 交换 + 结合）才抗重试。**

v4 里所有共享状态的合并函数都是 join：

| 键 | 合并语义 | 幂等 | 交换 | 结合 |
|---|---|---|---|---|
| 日志分片 `L.*` | 按 dot 取并集 | ✅ 同 dot 只进一次 | ✅ | ✅ |
| 站点指针 `V.*` | 逐字段取 max | ✅ | ✅ | ✅ |
| 注册表 `R.*` | 并集 + 取 max | ✅ | ✅ | ✅ |
| 快照 `S.*` | 按 obj 取最新 dot 覆盖（带 uptoSeq 单调保护） | ✅ | ✅ | ✅ |
| 内容 blob `B.*` | **不可变**（内容寻址） | — | — | — |

测试实测（T4）：**注入 190 次第三方抢写、触发 105 次 CAS 冲突重试后，40 个对象一个没丢，5 个客户端视图完全一致。**

这就是"数学上不可能丢更新"的实证，不是嘴上说的。

## 三、v3 的四个致命缺陷 → v4 的解法

| # | v3 | v4 |
|---|---|---|
| 1 | Get+Set 两条调用，**丢失更新** | 一律走 `_aupd()` 原子 RMW |
| 2 | 缓存永不失效，**跨房间读陈旧数据** | 每次同步强制按指针比对；指针 seq 未变则不再多读一个字节 |
| 3 | ID = 时间戳+`math.random`，**同秒启动的两个客户端序列完全相同 → dot 撞车** | **seq 块预留**：向 `Q.<app>.<site>` 原子申领 64 个连续 seq |
| 4 | 限流失败静默入队当成功 | 失败显式返回 `ERR`，绝不假成功 |

### seq 块预留（第 3 条的重点）

唯一 siteId 在"双开 / 多组件实例"场景下**根本做不到**（同一 uin 必然派生出同一个 id）。所以唯一性不能靠 siteId，要靠 seq：

```
进程 A 申领: base=100 -> 独占 [101,164]，写入 164
进程 B 同时: CAS 失败 -> 重新拉取 base=164 -> 独占 [165,228]
               区间不重叠 -> dot 永不撞车
```

`mergeFn(old) = old + 64` 在重试下依然正确：每次重试都基于**最新**的 base，拿到的新区间天然与已发出的区间不相交。

实测（T5）：两个实例共享同一 uin、同一 siteId，**20 个对象全部保留**（v3 在这种场景下必丢）。

## 四、CAS 长时间抢不到怎么办 —— 降级为什么仍然安全

写者极密时，CAS 可能一直抢不到。v4 在重试 6 次后**直接落盘最后一次合并结果**：

```lua
local nv = st.newVal or mergeFn(st.base)
self:_set(key, nv)
```

这不会丢数据，因为：
- `st.base` 是引擎最近一次交给我们的**真实当前值**（已包含所有我们见过的并发写）
- 合并是 join → 结果已含全部已见内容
- 唯一可能覆盖的是"同一瞬间、不在 base 里"的写 —— 那属于真正的并发窗口，由**下一轮同步补回**（op-log 只追加，不会消失）

这比无限重试或静默失败都好。

## 五、键布局

| 键 | 写者 | 值 | 上限 |
|---|---|---|---|
| `V.<app>.<site>` | 该站点自己 | `site\|maxShard\|maxSeq\|snapShard\|snapSeq\|hash` | 小 |
| `L.<app>.<site>.<n>` | 该站点自己 | 首行 `H\|site\|minSeq\|maxSeq\|count` + 每行一条 op | ≤ 48KB |
| `S.<app>.<site>` | 该站点自己 | 快照：每个 obj 只留最后一条有效 op | ≤ 1.9MB |
| `B.<app>.<hash>` | 任何人（**不可变**） | 原始字节，**支持不可打印字符** | ≤ 2MB |
| `R.<app>.<b>` | 多写（分桶打散热点） | `site:shard:seq;...` | 小 |
| `Q.<app>.<site>` | 该站点自己 | 已发放到的 seq（块预留计数器） | 小 |

全部键实测 **≤ 11 字节**（限制 50）、**可打印、无空格**。
全部值实测 **最大 242 字节**（限制 2MB）。

> `B.*` 用**原始字节**（官方确认 `Data.Map` 的 value 支持不可打印字符），所以大文件内容**不需要 base85**，省 25% 体积 + 编解码 CPU。只有 `Data.Table`（二维表）路径才必须可打印。

## 六、千人规模：配额是唯一的硬天花板

官方：`设置/获取` 每分钟 `30 + 在线人数 × 10`，且这是**全图共享**的。

人均预算 = `(30 + 10N) / N ≈ 10 次/分钟`（N 大时）。

**铁律：**

```
maxTrackSites × (60 / autoSyncSec) ≤ 10
```

| 配置 | 每人每分钟读 | 是否可行 |
|---|---|---|
| 8 站点 × 60s | **8** | ✅ 千人可行 |
| 16 站点 × 60s | 16 | ❌ 超预算 |
| 8 站点 × 30s | 16 | ❌ 超预算 |

### 稳态成本的实测（T12/T13，50 站点）

```
首次同步   164 次读（拉快照 + 全部分片）
第二次      50 次读
第三次      50 次读   ← 稳态：每个站点 1 次读（指针），注册表带 TTL 后不再计入
```

**关键优化：指针 seq 未变就一个字节都不多读。** 没有这条，50 站点稳态是 166 次，直接爆配额。

默认已按千人规模设定：`maxTrackSites = 8`、`autoSyncSec = 60`、`registryRefreshSec = 300`。

## 七、语义与冲突裁决

| 场景 | 行为 |
|---|---|
| 并发创建 | **都保留**（CRDT，无冲突） |
| 并发移动同一对象 | 按 HLC+dot 全序裁决，**全网一致**；记录 `concurrent_move` 冲突 |
| 移动成环 | 拒绝该 op，记录 `cycle` |
| 并发删除 vs 改 | 默认**删除优先**（`rmWins=true`），记录 `rm_wins`；关掉则按全序后者胜 |
| 内容 | 内容寻址 blob，**不可变**，天然无冲突 |

因果由 `op.dep` 承载，HLC 只做**确定性全序与新鲜度**，不承担因果 —— 这个分工不能颠倒，否则并发判定会错。

## 八、去中心化兜底

`useRegistry = false` 时完全不写共享注册表，只靠 `peerSites` 属性 + 同房间广播 → 仍收敛（T7 实测通过）。

适用场景：注册表被限流打爆、或变量库没配云变量。代价是要手工维护站点清单。

## 十、已知边界（诚实版）

1. **无跨键事务** —— 引擎没有。本设计用"不可变 blob + join 合并"绕开，不是真的有事务。
2. **未投递的本地 op 随进程死亡丢失** —— 语义上等于没提交，可接受。
3. **无线性一致** —— 读到的可能是几秒前的状态（新鲜度由 ⑪状态 明确报出，不假装是最新）。
4. **快照压缩不删除旧分片** —— 长期会撞 2MB，需要 GC（未实现；⑫压缩目前只写快照不删日志）。
5. **`ErrorCode` 枚举值与回调语义以真机为准** —— 脚本做了三重兜底，但**真机请先跑 ⑭环境自检**。
6. **测试跑在 Lua 5.1（lupa）**，但 `Data.Map` 是 mock。真实限流、真实回调时序需真机验证。

## 十一、真机上第一步做什么

1. 填 `kvVarId`（**必须是云变量**，否则跨房不通）
2. 填 `outEventId`
3. 调 **⑭环境自检** —— 确认 `UpdateValueAndCallback = ★存在`
4. 调 **⑬自检** —— 必须 `失败 0`
5. 调 **①初始化**，看打印的站点 ID 与"原子RMW=可用"
