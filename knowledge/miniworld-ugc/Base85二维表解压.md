# Base85 二维表解压：unquote 污染事故（2026-10-11 实测定位）

## 现象
日志报「抽样桶失败」「inflate 返回空」，启动自检「抽样桶加载 2/3」。

## 真凶
`unquote()` 无条件把 `""` 反转义成 `"`。但 **`"`（0x22）本身是合法 Base85 字符**
（字符集 0x21..0x75）。语料块里出现 `""` 是正常的 Base85 数据，被吃掉 1 字符
→ 位流错位 → 整个桶 inflate 返回 nil。

引擎若返回**已解析**的值（不带外引号），这次反转义纯属破坏。

## 量化（真实 25 万语料，256 桶）
| 版本 | 成功桶 |
|---|---|
| 旧 unquote（无条件反转义） | **28 / 256** |
| 修复后 | **256 / 256** |

即 87% 的语料根本没加载，全部走兜底。

## 修复
```lua
local function unquote(s)
    if type(s) ~= "string" then return s end
    local t = s
    if #t >= 2 and string.sub(t,1,1) == '"' and string.sub(t,-1) == '"' then
        t = string.sub(t, 2, -2)
        -- 只有确认是「原始带引号 CSV 字段」才反转义
        if string.find(t, '""', 1, true) then t = string.gsub(t, '""', '"') end
    end
    return t
end
```
引擎返回原始带引号字段 → 仍正确；返回已解析值 → 不再破坏。

## 排查方法（可复用）
用 lupa(lua51) + 引擎 mock 跑端到端，喂真实 CSV 行数据，
调 `Script:DiagBucket(bid)` 打印每个偏移的块数/字符数/结果。
**关键信号：块数对但字符数差几个 → 是取值函数污染，不是偏移错。**
本次即靠「89 块 / 22767 字符 vs Python 侧 22770」这 3 字符之差锁定的。

## 附带发现
- 偏移自动探测曾把 **off=5 误判为成功**（坏数据却含 \1，通过校验）。
  → 校验不能只看「含分隔符」，应比对条目数/解压长度是否合理。
- 不同表的行偏移不同（表内 off=2），写死偏移必然崩。
