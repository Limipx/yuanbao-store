# 全服去中心化文件夹系统 · 设计原理与使用说明

> 一句话：**云服全服广播本身就是一条「原子广播（Atomic Broadcast）」通道**——
> 一次发送，所有房间都收到。有了原子广播，共识几乎免费：不需要 Leader、不需要投票、
> 不需要 PoW/PoS。剩下的只是"按同一规则重放同一份日志"，各房间必然收敛到同一状态。

---

## 一、问题设定

| 项 | 现状 | 约束 |
|---|---|---|
| 节点 | 云服房间 | 随时可能关闭、随时新建（churn） |
| 存储 | 房间字符串数组 `Data.Array(playerId=nil)` | 只在房间内生效，房间重启后仍在 |
| 通信 | 云服全服广播 | 单向、延迟 ~10s、无回执、可能重复/乱序 |
| 禁项 | **不用 KV 表** | 全部靠广播 + table |

目标：所有房间共享同一棵目录树，房间关了数据不丢。

---

## 二、为什么区块链思想在这里是"对症"的

房间 = 节点，广播 = gossip，房间数组 = 本地账本，房间关闭 = 节点掉线。这不是比喻，是同构：

| 区块链 / 分布式概念 | 本系统对应 |
|---|---|
| 节点（peer） | 云服房间 |
| P2P gossip 网络 | 云服全服广播 |
| 账本（append-only log） | 房间数组里的操作日志 |
| 区块哈希链 | 每个条目带 `prev` 指向本房间上一条的哈希 |
| Merkle 树 | 全局状态根（用于比对"我们是否一致"） |
| 内容寻址 / CAS | 文件内容按 MD5 去重 |
| 共识 | **Lamport 时钟 + (clock,rid,seq) 确定性全序** |
| 全节点全量复制 | 每个房间都存全量日志 → 抗房间关闭 |
| anti-entropy / gossip 修复 | 心跳 + 连续水位 + 补发 |
| 出块（batching） | 多条操作打包进一条广播 → 摊薄 10s 延迟 |
| 拜占庭节点 | 伪造/损坏条目被哈希校验直接丢弃 |

### 但有三件事**不需要**（这是联盟链，不是公链）

1. **不需要 PoW / PoS** —— 它们解决的是"陌生人如何建立信任"（女巫攻击）。
   这里所有房间都属于你自己的地图，准入靠"消息 ID 只有我们知道"，是**许可链**。
2. **不需要 Leader 选举 / 投票（Raft、PBFT）** —— 选举是为了在普通网络上造出全序。
   云服广播已经把全序通道送上门了。
3. **不需要挖矿/代币激励** —— 没有陌生人，没有作恶动机需要经济博弈来抑制。

### 一个关键的理论点

> **原子广播 ≒ 共识**（Chandra & Toueg 1996）：在异步系统里，两者可互相实现。
> 反过来，有了原子广播，共识变得平凡——每个节点按**同一个确定性顺序**重放日志即可。

所以本系统的"共识"就是一句排序规则：

```lua
table.sort(log, function(a,b)
    if a.clock ~= b.clock then return a.clock < b.clock end   -- Lamport 时钟
    if a.rid   ~= b.rid   then return a.rid   < b.rid   end   -- 房间 ID（打破并列）
    return a.seq < b.seq                                       -- 房间内序号
end)
```

**所有房间算出同一个排序 → 重放出同一棵树 → 状态一致。** 没有投票，没有协调。

## 三、架构分层

```
┌─────────────────────────────────────────────────────────┐
│ 开放函数层  Mkdir/Write/Read/List/Delete/Move/Copy/Find  │
├─────────────────────────────────────────────────────────┤
│ 状态机层    排序后的日志 → 重放 → 目录树 (table 内存态)   │
├─────────────────────────────────────────────────────────┤
│ 共识层      Lamport 时钟 + 确定性全序 (无 Leader)         │
├─────────────────────────────────────────────────────────┤
│ 完整性层    每房间哈希链 + 全局 Merkle 状态根              │
├─────────────────────────────────────────────────────────┤
│ 同步层      连续水位(CW) + 心跳 + 反熵补发 + 随机退避      │
├─────────────────────────────────────────────────────────┤
│ 存储层      房间字符串数组 (playerId=nil), 追加式日志      │
│ 通信层      云服广播 PushCloudServerMsg (一个 ID 多路复用) │
└─────────────────────────────────────────────────────────┘
```

## 四、五个核心机制

### 1. 日志条目与哈希链

```
seq | clock | rid | prev | hash | op | path | val | arg
                     │        │
                     │        └─ hash = MD5(除 hash 外的所有字段)
                     └─ prev  = 本房间上一条的 hash
```

- **每个房间一条独立链**（不是全局单链）。因为日志排序会变（晚到的旧时钟条目会插到中间），
  **位置式全局链必然断裂**；按房间分链则 seq 稠密、定义良好。
- 全局完整性用**状态 Merkle 根**表达：`root = MerkleRoot(所有条目 hash)`。
  两个房间根相同 ⇒ 日志集合相同。这比逐条比对便宜得多。

### 2. Lamport 全序

- 本地写：`clock = clock + 1`
- 收到条目：`clock = max(clock, e.clock)`
- 排序：`(clock, rid, seq)`

Lamport 时钟保证"若 A 因果先于 B，则 clock(A) < clock(B)"；
无因果关系的并发写则靠 `rid` 做确定性打破并列（等价于 Last-Writer-Wins，但**所有人都同意谁是 Last**）。

> 实测：A 与 B 同时对 `/hot` 写入不同值，三房间最终都得到同一个值，Merkle 根一致。

### 3. 连续水位（Cumulative Watermark）—— 本系统最关键的一处

**踩过的坑**：最初用"最大 seq"做版本向量。乱序投递会让 B 持有 `1..24` 和 `100..112`，
于是 VV 记成 112，A 认为 25–99 都有了，**永远不再补发 → 收敛死锁**（实测卡在 12 条不动）。

改为**连续水位**：`cw[rid] = 满足 1..c 全部到齐的最大 c`（就是 TCP 的累积确认）。
心跳广播的是 `cw`，补发的是"水位以上"的条目，保证单调推进。

再加上**放大块**：应答者除水位窗口外，再按自身 rid 散列抓一个对齐块，
使 N 个房间回的批次尽量不重叠（gossip 里的 divergent selection）。

> 实测：200 条日志，全新房间 17 轮同步完成；8 房间混沌场景下全部收敛到同一根。

### 4. 反熵与抑风暴

- 进图 / 周期性：广播 `HLO|<连续水位>;<状态根>`
- 收到 HLO 的房间：算出"我有他水位以上的条目"，打包成 `BLK|...` 广播回去
- **抑风暴**：对方已有数据时 15% 概率本轮不答（他还会再喊）；
  对方是空房间（水位全 0）则必答，保证新房间的首次拉取一定成功
- 条目按 `(rid,seq)` 去重，重复投递只增 `dup` 计数，不产生副作用

### 5. 抗房间关闭 = 全量复制

每个房间都持有**完整**日志（不是分片）。房间关闭后，数据仍在其他所有房间里。

> 实测：13 次随机关闭后，全部 10 个存活房间仍持有全部 226 条，根一致。

代价：**单房间容量 = 全服数据量**。这是"不用 KV 表"的必然代价。

## 五、一个广播当无数个用

广播 ID 必须在触发器里预设、数量有限。按你的 MiniBus 先例，用**信封路由**：

```
DCCFS \1 BLK \1 <载荷>      日志条目块
DCCFS \1 HLO \1 <水位>;<根>  心跳 / 请求补齐
```

只占 param1，三种通道都能用同一套。

## 六、怎么用

### 配置（组件属性）

| 属性 | 默认 | 说明 |
|---|---|---|
| `arrId` | `FSLog` | 房间数组 ID（自动派生 `FSLog_rid` 存本房间 ID） |
| `msgId` | 空 | **必填**，触发器里预设的云服广播消息 ID |
| `roomId` | 空 | 留空 = 发全服；填了 = 定向房间 |
| `blockSec` | 10 | 出块间隔（秒），建议 ≥ 广播延迟 |
| `blockMax` | 12 | 每块最大条目 |
| `blockChars` | 3500 | 每块最大字符（防单条广播超长） |
| `shardBytes` | 512 | 超过则自动分片（hex 后翻倍） |
| `helloSec` | 60 | 心跳周期（秒） |
| `autoTimer` | 开 | 自动建定时器驱动 Tick |

### 接线

1. 触发器里建一条**云服广播消息**，把它的 ID 填进 `msgId`
2. 组件挂上脚本，`OnStart` 会自动 `Init` + 注册 `AddCloudSeverEvent` + 发一次 `Sync`
3. 定时器驱动 `Tick`（`autoTimer=1` 时自动建），或手动周期调用

### 开放函数

| 函数 | 返回 | 说明 |
|---|---|---|
| `Init()` | bool | 初始化（手动调用亦可，会自动注册广播监听） |
| `Tick()` | string | 出块 + 心跳 |
| `OnCloudEvent(...)` | string | 广播入口，接到预设消息 ID 的回调上 |
| `Mkdir(path)` | string | 建目录 |
| `Write(path, content)` | string | 写文件（超 512B 自动分片；`[]` 追加、`[-1]` 末尾） |
| `Read(path)` | string | 读文件 |
| `List(path)` | string | 列子项（逗号分隔） |
| `Delete(path)` | string | 删除子树 |
| `Move(a,b)` / `Copy(a,b)` | string | 移动 / 复制 |
| `Find(pattern)` | string | 通配查找：`*` 单段内通配，`**` 跨多段 |
| `Stat(path)` | string | 路径 / 类型 / 大小 / 时钟 / 归属房间 |
| `Digest()` | string | 房间 ID + 连续水位 + Merkle 根 + 日志数 |
| `Status()` | string | 收发/去重/坏条目/出块计数 |
| `Sync()` | string | 立即广播一次心跳（请求补齐） |
| `Compact()` | string | 写快照 + 逻辑剪枝 |
| `Verify()` | string | 校验全部哈希链，返回 bad 数 |
| `NetProbe()` | string | 探测广播接口与 bit 库来源 |

## 七、复杂度

符号：`n` 日志条数 · `c` 单层子项 · `d` 路径深度 · `m` 文件字节 · `B`=512 分片 · `P` 房间数

| 操作 | 时间 | 说明 |
|---|---|---|
| `Write` 小文件 | O(m + n log n) | 一次 emit + 重排序 |
| `Write` 大文件 | O(m + ⌈m/B⌉·n log n) | 每分片一条 |
| `Read` | O(d + m) | 内存态直读 |
| `List` | O(c) | 子项索引 |
| `Find` | O(n_tree) | 遍历内存树做通配 |
| `Tick` 出块 | O(n) | 状态根 Merkle |
| 收到 `BLK` | O(k + n log n) | k=条目数，含重排序 |
| 收到 `HLO` | O(n log n) | 算 missing + 排序 |

**广播次数才是真瓶颈**（不是 CPU）：

- 每 `blockSec` 最多 1 次出块广播
- 每 `helloSec` 最多 1 次心跳
- 收到心跳时最多 1 次补发
- **全量同步 N 条日志 ≈ ⌈N / blockMax⌉ 轮**，每轮约 2× 广播延迟（20s）

建议：日志量大时把 `blockMax` 调到 30–50（注意 `blockChars` 别超单条广播上限）。

## 八、诚实说明：保证到哪一步

**做到的**

- ✅ **最终一致性（收敛）**：只要还有 ≥1 个房间持有数据，所有房间最终会收敛到同一状态
- ✅ **抗房间关闭**：全量复制，13 次随机关闭后仍完整
- ✅ **抗重复投递**：幂等，实测重复投递不产生重复条目
- ✅ **抗损坏/伪造**：哈希不匹配的条目直接丢弃（实测坏数据未污染状态）
- ✅ **房间重启**：数组持久，重启后内容与根完全一致

**做不到的**

- ❌ **强一致性 / 线性一致**：读的是本地内存态，可能落后至多一个同步周期（~10–60s）。
  这是 CAP 下选了 AP——10s 延迟的通道注定拿不到 C。
- ❌ **所有房间同时关闭 ⇒ 数据全丢**。没有 KV 表就没有跨房间生命周期的存储。
  这是"不用 KV"的硬边界，不是 bug。
- ❌ **写后读（自己写自己立刻读）在本房间一定可见**，但别的房间不保证立刻可见。
- ❌ **FLP 不适用但也不免费**：我们不做"终止性决议"，只做收敛，所以绕过了 FLP；
  代价是没有"提交成功"这个明确时刻。

**未实现**

- 未做崩溃后的日志重放（WAL）。多步操作中途崩溃可能留下部分分片残留，
  用 `Find` + `Delete` 手工清理。
- `Compact()` 只做**逻辑**剪枝（写快照 + 标记），数组仍会增长，不回收物理空间。
- 权限/加密未做（本版聚焦同步与容灾）。

## 十一、开发过程中踩到的真坑（都修了）

1. **`bor` 传了 4 个参数**：模拟器与算术回退的 `bor` 只收 2 个，高位字节被静默丢弃
   → MD5 对 ≥2 字节输入全错。改为**只用两参数嵌套调用**（不赌引擎 bit 库是否可变参数）。
2. **`self:Write()` 拿不到**：`self` 是组件实例，不保证以 `Script` 为元表
   → 内部调用统一改 `Script.Write(self, ...)`。
3. **云服监听注册写在 `OnStart`**：手动调 `Init` 时收不到包 → 移入 `Init`。
4. **`reindex` 拿 hash 字符串和数字比大小** → 运行时崩溃。
5. **版本向量用"最大 seq"** → 乱序投递产生空洞，收敛**死锁**在 12 条。改用连续水位。
6. **所有房间回同一批最低条目** → 互相完全冗余，收敛不随房间数提升。改为排序前缀 + 散列放大块。

## 十二、调参建议

| 场景 | 建议 |
|---|---|
| 房间多（>10）、日志量大 | `blockMax` 30–50，注意 `blockChars` 别超广播单条上限 |
| 想让新房间更快拉全量 | 调小 `helloSec`（如 30），或进图时连发几次 `Sync` |
| 广播很挤 | 调大 `blockSec`；利用 15% 退避本身的分流 |
| 单房间日志太大 | 定期 `Compact()` 写快照（只做逻辑剪枝） |
| 怀疑数据不一致 | 对比各房间 `Digest()` 的 `root`；`Verify()` 查 `bad` |
